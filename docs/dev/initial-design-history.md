## 三、最关键的算法设计要点

这是日麻项目最容易翻车的地方，先把思路画清楚：

### 1. 牌的编码
推荐用 **0-33 的 int 表示牌型**（万 0-8、筒 9-17、索 18-26、字 27-33），赤五用单独标志位。整个手牌可以用一个长度 34 的数组 `counts[34]` 表示，听牌判定就是数组操作，非常快。

### 2. 听牌分解（核心算法）
14 张和牌型 = **4 面子 + 1 雀头**，加上两个特殊型（七对子、国士无双）。推荐做法：

- 先枚举雀头（每种牌作雀头），剩 12 张
- 对每种花色独立做 DFS：依次尝试取顺子 / 取刻子 / 跳过
- 字牌只能刻子或杠
- **听牌 = 13 张时，枚举 0-33 中每张作为第 14 张测试能否和牌**

> 这个算法的实现网上有现成的 Python 库可参考，比如 `mahjong`（PyPI）。建议**先调通这个库的接口确认规则正确，再考虑自己重写**——重写有助于理解，但不必从零开始。

### 3. 役判定
役的判定要**对同一手牌的所有合法面子分解**取最高番组合（因为有些手牌可能分解出"平和"也可能分解出"三色同顺"，要取番最高那种）。这是一个枚举+评分问题。

### 4. 振听
需要维护：
- 自家河（自己已打出的牌）
- 自家听牌列表
- 当前是否在立直状态、立直后摸牌巡数
- 同巡他家打出的牌（用于同巡振听）

### 5. 3麻特殊规则（容易遗漏）
- 没有万子 2-8，牌山 108 张
- 北抜き（拔北宝牌）
- 通常没有"喰い断"和"食替"，但有些规则允许
- 点数翻番规则、ツモ损规则因流派而异（需要做成可配置）

## 三、关键设计决策

下面几个点是经验上日麻项目最容易翻车的，提前定死：

**1. 牌的编码**

```
万 1m-9m  →  0-8
筒 1p-9p  →  9-17
索 1s-9s  →  18-26
字 东南西北白发中  →  27-33
赤五：单独的 bool 标志，不占编码位
```
手牌主表示用 `counts: int[34]`，所有快速判定都用这个；只有渲染、牌谱、显示时才转回 `"1m 2m 3m..."` 字符串。

**2. 局面状态对象**

用 `frozen dataclass` 表示 `GameState`，规则引擎每个动作返回**新的** `GameState`，不可变。好处：
- 牌谱回放就是状态序列
- 单元测试只需断言新旧状态差
- 后期接入 AI 训练自然就是 `(state, action) → state'`

**3. 役判定的双重枚举**

同一手 14 张可能有多种合法分解（比如 222 333 444 既能算"三色同顺"也能算"三暗刻"，取番高那种）。所以：
```
for 分解 in 所有合法分解:
    for 役 in 役表:
        判定该役在此分解下是否成立
    汇总 → 该分解总番数
取所有分解中番数最高者
```

**4. 联机的反作弊核心原则**

- 服务端持有完整牌山，**客户端永远只看到自己手牌 + 公开信息**
- 摸牌时服务端推送下一张到该玩家，不向他家推送
- 听牌/和牌/役判定的"提示"，服务端算完再下发（客户端不持有规则引擎）
- 所有动作（打哪张、吃/碰/杠/立直/和）由服务端校验合法性

**5. 雀魂规则要点（M1 之前必须列清楚）**

我建议你在 `docs/rules.md` 里明确写下：
- 半庄 / 东风 切换
- 红宝牌数量（雀魂金之间通常 3 枚红五）
- 流局满贯、流局听牌罚符
- W立直、海底捞月、河底捞鱼、抢杠、岭上开花、岭上开花+杠宝
- 食断（雀魂默认有）
- 取消役：雀魂没有"古役"
- 4 杠流局、4 风连打流局、9 种 9 牌
- 一发被吃断
- 3 麻特有：北抜き作为宝牌、ツモ损（雀魂规则）

## 为什么你的节奏更优

**1. 单一规则集，避免过早抽象**

3 麻和 4 麻虽然底层共用大部分代码，但差异点（北抜き、牌山构成、ツモ损点数、流局规则）会渗透到牌山、役、符番好几个模块。如果一开始就要兼顾两种模式，你会在 M1-M4 反复纠结"这个接口要不要为 3 麻预留参数"。

**先把 4 麻彻底做对，再做 3 麻**，反而能让 3 麻的引入变成一次有目的的重构——那时候你已经知道哪些地方真的有差异，抽象会更自然、更准。这就是"先具体后抽象"的工程原则。

**2. CLI 先于前端，价值密度最高**

前端工作量大但不产生新逻辑。CLI 能完整验证规则引擎，对项目本身是闭环的；而前端只是把现有逻辑可视化。先 CLI 的好处：
- 规则有 bug 时调试成本极低（看 stdout 即可）
- 整局跑通后才知道哪些 API 真的需要，避免前端做完发现要改接口
- CLI 本身可以作为长期的回归测试工具

**3. AI 放最后是对的**

AI 推荐打牌 / 人机对手需要：稳定的规则引擎 + 大量牌谱数据 + 训练流程。这些前置条件没满足时做 AI 就是空中楼阁。而且联机做完后，你的服务端本身就是一个完美的 AI 训练环境（自我对弈）。

**唯一需要微调的点**：联机和前端的先后我建议**联机后端先于前端**，原因下面讲。

## 关于 M7 和 M8 顺序的建议

你原本的顺序是"前端 → 联机"，但我建议**调换成"联机后端 → 前端"**。理由：
